# glimpse

A tiny Digma-style trace collector in one binary. It ingests OTLP/HTTP traces
(`POST /v1/traces`, protobuf + JSON, see `cmd/server/ingest.go`), stores spans
in SQLite, and serves insights (`cmd/server/api.go`) plus an embedded UI
(`cmd/server/ui/index.html`). Migrations are embedded via `migrations.go` and
run on startup — the binary is self-contained. Default port is 4318 (the OTLP
standard) so agents need no port config. See README.md for usage.

The UI follows the Quire design system. `cmd/server/ui/tokens.css` and
`cmd/server/ui/fonts/` are copies from Quire; use its tokens by name, never raw
values. Light only.

Quire version: 3

## Architecture

This is a Go API built with three composable tools and SQLite:

- **Huma** (github.com/danielgtaylor/huma/v2) — HTTP framework that generates OpenAPI 3.1 specs from Go struct tags
- **SQLC** (sqlc.dev) — Generates type-safe Go code from annotated SQL queries
- **Goose** (github.com/pressly/goose) — Database migrations using plain SQL files
- **SQLite** (modernc.org/sqlite) — Embedded database, pure Go driver, no CGO required

### How the pieces connect

1. Goose manages schema via SQL migration files in `sql/migrations/`
2. SQLC reads those migrations as schema source of truth + reads query files from `sql/queries/`
3. SQLC generates typed Go code into `db/` package
4. Huma reads Go struct tags to generate OpenAPI spec, validation, and docs
5. Handlers in `cmd/server/main.go` connect Huma inputs to SQLC queries

No ORM. No runtime reflection. No external database server. The entire database is a single file at `./data/glimpse.db`.

## Development Workflow

### Adding a new feature

1. Write a Goose migration in `sql/migrations/` with sequential numbering
2. Write SQLC queries in `sql/queries/` with annotations (`:one`, `:many`, `:exec`)
3. Run `make generate` to regenerate the `db/` package
4. Define Huma input/output structs with struct tags in `cmd/server/main.go`
5. Register the operation with `huma.Get`, `huma.Post`, etc.
6. Run `make migrate-up` to apply migrations
7. Run `make run` to start the server

### Key commands

- `make generate` — Run SQLC to regenerate `db/` from SQL
- `make migrate-up` — Apply all pending Goose migrations
- `make migrate-down` — Roll back the last Goose migration
- `make run` — Generate code and start the server
- `make backup` — Copy the .db file with a timestamped name

## Coding Conventions

### Migrations

- Use sequential numbering: `001_`, `002_`, etc.
- Always include both `-- +goose Up` and `-- +goose Down` blocks
- Migrations are the schema source of truth — SQLC reads them directly
- Keep migrations small and focused on one change
- Use SQLite types: `INTEGER`, `TEXT`, `REAL`, `BLOB`
- Use `INTEGER PRIMARY KEY AUTOINCREMENT` for auto-incrementing IDs
- Store timestamps as TEXT with `DEFAULT (datetime('now'))`
- SQLite does not enforce column types strictly — the type names are advisory

### SQL Queries (SQLC)

- One file per resource in `sql/queries/`
- Use SQLC annotations: `:one` (single row), `:many` (multiple rows), `:exec` (no return)
- Use `?` for positional parameters (not $1, $2 — that is PostgreSQL syntax)
- `RETURNING *` works in SQLite 3.35+ for INSERT/UPDATE/DELETE
- Query names become Go method names (e.g., `-- name: GetWidget :one` becomes `queries.GetWidget()`)

### Generated Code

- Never edit files in `db/` manually — they are regenerated by `sqlc generate`
- The `db/` package exports a `Queries` struct with methods matching your SQL query names
- `Queries` accepts a `database/sql` `*sql.DB` or `*sql.Tx` and provides typed methods
- Use `queries.WithTx(tx)` for transaction support

### Huma HTTP Operations

- Define input/output as Go structs with struct tags
- Use `path`, `query`, `header` tags for request parameters
- Use `json` tags for request/response body fields
- Use `doc`, `example`, `required`, `maxLength`, `enum` tags — they feed into the OpenAPI spec and validation
- Huma validates inputs before the handler runs — invalid requests get a 422 automatically
- Return `huma.ErrorXXX()` for error responses (e.g., `huma.Error404NotFound()`)

### Error Handling

- Wrap errors with context: `fmt.Errorf("creating widget: %w", err)`
- Use Huma error helpers for HTTP errors: `huma.Error404NotFound()`, `huma.Error400BadRequest()`
- Let Huma handle validation errors (they come from struct tags)

### Database

- Database path from `DB_PATH` env var, with fallback to `./data/glimpse.db`
- The server enables WAL mode on startup (`PRAGMA journal_mode=WAL`) for better read concurrency
- Foreign keys are enabled on startup (`PRAGMA foreign_keys=ON`) — SQLite has them off by default
- The `*sql.DB` handle is created in main and passed to `gendb.New(database)`
- WAL mode creates `-wal` and `-shm` companion files next to the .db file — these are normal
- To back up the database, use `make backup` or simply copy the .db file (safe while WAL is enabled)

### SQLite-specific notes

- SQLite uses dynamic typing — column type names are advisory, not enforced
- `ALTER TABLE` is more limited than PostgreSQL: you can ADD columns but not DROP or ALTER them in older SQLite versions. For column removal, create a new table, copy data, drop old, rename new.
- There is no `BIGSERIAL` — use `INTEGER PRIMARY KEY AUTOINCREMENT`
- There is no `TIMESTAMPTZ` — store timestamps as TEXT in ISO 8601 format
- No `ENUM` type — enforce allowed values in application code or with CHECK constraints
- Concurrent writes are serialized (one writer at a time). WAL mode allows concurrent readers alongside a single writer. This is fine for most API workloads.

## API Documentation

Huma auto-generates and serves:
- OpenAPI 3.1 spec at `/openapi.json`
- Interactive docs at `/docs`

The spec is generated from Go types at startup — it is always in sync with the code.

## Dependencies

- `github.com/danielgtaylor/huma/v2` — HTTP framework + OpenAPI generation
- `modernc.org/sqlite` — Pure Go SQLite driver (no CGO, no gcc needed)
- `github.com/pressly/goose/v3` — SQL migration tool
- SQLC CLI — installed separately (`go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest`)
- Goose CLI — installed separately (`go install github.com/pressly/goose/v3/cmd/goose@latest`)
