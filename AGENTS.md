# glimpse: guide for coding agents

glimpse is a small trace collector in one Go binary. It ingests OTLP/HTTP
traces, stores spans in SQLite, and serves insights, a plain-text trace digest
for LLMs, execution plans, and an embedded UI. README.md has the user view.

Module: `github.com/lab900/glimpse`. Go 1.25. No CGO, and it must stay that
way: releases cross-compile for linux, macOS and Windows with `GOOS`/`GOARCH`.

## Layout

```
cmd/server/
  main.go          env, SQLite open + migrations, router, shutdown, purge loop
  ingest.go        POST /v1/traces: OTLP protobuf and JSON to span rows
  api.go           Huma operations: endpoints, traces, insights, stats, delete
  digest.go        GET /api/traces/{id}/digest: one trace as plain text
  plan.go          POST /api/queryplan and the SQL Server plan cache lookup
  plan_pg.go       Postgres plans: EXPLAIN (GENERIC_PLAN), never ANALYZE
  *_test.go        tests on a real temporary SQLite database
  ui/              embedded UI: index.html, tokens.css, fonts, favicon
sql/migrations/    goose migrations, the schema source of truth
sql/queries/       sqlc queries
db/                generated by sqlc. Never edit by hand.
migrations.go      embeds sql/migrations into the binary
skill/SKILL.md     Claude Code skill that reads a running glimpse
docs/screenshots/  README images
Dockerfile, .github/workflows/   image, CI, release
```

## Commands

```sh
make tools      # install sqlc and goose (one time)
make generate   # sqlc generate, after any change in sql/
make test       # go test ./...
make run        # generate, then start on 127.0.0.1:4318
make build      # ./glimpse with the version from git
go vet ./... && gofmt -l .   # must be clean before a commit
```

CI, the Dockerfile and the release workflow use plain `go build`, so `db/`
must be committed and up to date with `sql/`.

## Rules

- **Schema changes** go in a new migration `sql/migrations/NNN_name.sql` with
  `-- +goose Up` and `-- +goose Down`. Never edit an applied migration. Old
  databases must still migrate at start; `server_test.go` has a test for this.
- **Queries** go in `sql/queries/spans.sql` with sqlc annotations and `?`
  parameters. Run `make generate` and commit `db/`.
- **HTTP operations** use Huma structs with tags (`query`, `path`, `json`,
  `doc`). The OpenAPI spec is generated from them. Return `huma.ErrorXXX`.
  Plain handlers (ingest, digest, UI) are registered on the mux in `main.go`.
- **Errors:** wrap with context, `fmt.Errorf("listing traces: %w", err)`.
- **Captured SQL is never executed.** Plans come from the SQL Server plan
  cache or from Postgres `EXPLAIN (GENERIC_PLAN)` in a read-only transaction.
  Do not add `ANALYZE` or anything that runs a captured statement.
- **No authentication exists.** The default bind is `127.0.0.1` (`HOST`).
  Do not change that default.
- **Ingest must stay cheap.** Each index slows it down. Add an index only when
  `EXPLAIN QUERY PLAN` shows a scan that it fixes.
- **The digest is an API for LLMs.** Its output must be deterministic. Keep it
  compact, and keep the one-service format stable.
- **Tests** use the standard library only, on a temporary SQLite file with the
  embedded migrations (see the helpers in `server_test.go`). Use a spare port
  for manual runs, not 4318: the user can have glimpse running there.
- **Dependencies:** add one only when the standard library cannot do the job,
  and only if it is pure Go.

## UI

`cmd/server/ui/index.html` is one file with inline CSS and JS, no build step.
It follows the Lab900 look: dark chrome bar, orange for actions, teal and mint
for accents, Lato. `tokens.css` holds all values; use its tokens by name and
never write a raw colour or size in `index.html`. Light theme only.

After a visible UI change, update `docs/screenshots/`.

## SQLite notes

- Timestamps are integer nanoseconds (`start_ns`, `duration_ns`).
- Pragmas (WAL, busy_timeout, foreign keys) are set in the DSN in `openDB`,
  because they are per connection.
- `(trace_id, span_id)` is unique, and inserts ignore conflicts, because OTLP
  exporters retry.
- Writes are serialized. One export request is one transaction.

## Release

Push a tag `vX.Y.Z`. `.github/workflows/release.yml` builds six binaries with
checksums and creates the GitHub release. No Docker image is published; the
`Dockerfile` is for users who build their own.
